# Week 2 contract: Quantum Pet, Inbox, Invites

Builds on docs/CONTRACT.md (stack facts, lint rules, design classes, pq.ts API) and the live Worker in worker/index.ts (helpers, D1 `DB`, Helius `RPC_URL`, rate-limit table `ratelimit`, existing routes /api/passports, /api/seals, /api/stats, /api/scan, /api/rpc). Two modules are written in parallel; the integrator wires them into the router and the scheduled handler.

Shared conventions for both modules:
- New Worker code lives in its own file (`worker/pet.ts`, `worker/x.ts`, `worker/inbox.ts`) exporting `handleX(request, env, ctx, parts: string[], url: URL): Promise<Response | null>` where `parts` is `url.pathname.split("/").filter(Boolean)` (so `parts[0] === "api"`). Return `null` when the route is not yours. Do not edit `worker/index.ts` (the integrator adds two delegation lines before `notFound()` and the `scheduled` export).
- Each module defines its own small helpers (json with CORS headers, badRequest, readJson with a size cap) rather than importing them from index.ts. CORS headers: `Access-Control-Allow-Origin: *`, `Access-Control-Allow-Methods: GET,POST,DELETE,OPTIONS`, `Access-Control-Allow-Headers: Content-Type, Authorization`. Answer OPTIONS with 204.
- Rate limiting uses the existing D1 table `ratelimit(key TEXT PRIMARY KEY, window_start INTEGER, count INTEGER)` with this exact statement (fixed window):
  `INSERT INTO ratelimit (key, window_start, count) VALUES (?1, ?2, 1) ON CONFLICT(key) DO UPDATE SET count = CASE WHEN ratelimit.window_start = excluded.window_start THEN ratelimit.count + 1 ELSE 1 END, window_start = excluded.window_start RETURNING count` with key `${bucket}:${clientIp}` and `window_start = floor(Date.now() / periodMs)`. Over the limit → 429 JSON `{ error: "rate limited", retryAt }` with `Retry-After`. Client IP = `cf-connecting-ip` header or "anon".
- Env fields each module may read (the integrator adds them to the Env interface): `DB: D1Database`, `RPC_URL?: string`, `SITE_URL?: string` (default "https://dirac.deeper-cf.workers.dev"), `X_API_KEY?`, `X_API_SECRET?`, `X_ACCESS_TOKEN?`, `X_ACCESS_SECRET?` (all strings). Modules declare their own `Env` interface with the fields they use (structural typing makes them compatible).
- Migrations: Module A writes `migrations/0003_pet.sql`, Module B writes `migrations/0004_inbox.sql`. `CREATE TABLE IF NOT EXISTS` only.
- Frontend: static export, client pages under `src/app/<route>/page.tsx` plus a `layout.tsx` with `metadata` (title, description) like the existing `/scan`. Use the design classes; chapter headers via `ChapterHeader` with `as="h1"`; wallet via `useWallet()` from `@/lib/solana/wallet`; session keys via `useSession()` from `@/components/app/session` (fields: `passport`, `keys` (PassportKeys with kemSk/dsaSk), `selfSig`, `walletSig`, `anchorTx`). API base via `API_BASE` from `@/lib/api`.

## Module A: Quantum Pet

### Physics (worker/pet.ts, pure functions exported for tests)
- 10 qubits, state vector of 1024 complex amplitudes stored as two Float64Arrays (re, im); basis index bit i = qubit i.
- Gates: `H(q)`, `X(q)`, `RY(q, theta)`, `CNOT(c, t)`, `measure(q)` (p1 = Σ|a|² over indices with bit q set; outcome drawn with `crypto.getRandomValues`; collapse and renormalise; returns 0|1), `measureAll()` (sample one basis state from |a|², returns the 10-bit string, bit 0 first).
- Day start state: |0…0⟩ then H on every qubit.
- Serialisation: `{ re: number[], im: number[] }` JSON (2048 numbers), round to 1e-12.
- Traits from a 10-bit string b (bit i = qubit i): form = b[0..2] → ["cat","virus","black hole","cube","moth","jellyfish","crystal","fox"], character = b[3..4] → ["curious","sleepy","chaotic","stoic"], ability = b[5..7] → ["phase shift","tunneling","entanglement","decoherence","teleportation","superposition","interference","measurement"], palette = b[8..9] → ["ice","ember","violet","mint"]. Export `TRAITS` and `traitsFromBits(bits)`.
- Probabilities: `formProbabilities(state)` → Record<form, p>; `topOutcomes(state, n)` → [{ bits, p }]; `qubitP1(state)` → number[10]. `pCat` = probability of form "cat".

### Storage (migrations/0003_pet.sql)
```sql
CREATE TABLE IF NOT EXISTS pet_state (id INTEGER PRIMARY KEY CHECK (id = 1), day INTEGER NOT NULL, day_started_at INTEGER NOT NULL, state TEXT NOT NULL, protected TEXT NOT NULL DEFAULT '{}', actions_today INTEGER NOT NULL DEFAULT 0, updated_at INTEGER NOT NULL);
CREATE TABLE IF NOT EXISTS pet_days (day INTEGER PRIMARY KEY, bits TEXT NOT NULL, form TEXT NOT NULL, character TEXT NOT NULL, ability TEXT NOT NULL, palette TEXT NOT NULL, actions INTEGER NOT NULL, p_top REAL NOT NULL, measured_at INTEGER NOT NULL, posted_at INTEGER);
CREATE TABLE IF NOT EXISTS pet_actions (id INTEGER PRIMARY KEY AUTOINCREMENT, day INTEGER NOT NULL, gate TEXT NOT NULL, q INTEGER NOT NULL, t INTEGER, outcome INTEGER, client TEXT NOT NULL, at INTEGER NOT NULL);
CREATE INDEX IF NOT EXISTS pet_actions_day ON pet_actions(day, at);
```
First run (no row): create day 1 with the day-start state; day 1's "current form" is "cat" (there is no previous collapse). `collapseAt` = next 00:00 UTC after `day_started_at`.

### Routes
- `GET /api/pet` → `PetState` (below). If `Date.now() >= collapseAt` and the day has not been collapsed yet, collapse lazily first (same code path as the cron) so the state is always fresh even if the cron missed.
- `POST /api/pet/act` body `{ gate: "H"|"X"|"CNOT"|"MEASURE"|"PROTECT"|"MUTATE", q: number, t?: number }`. Rules: q (and t for CNOT, t ≠ q) in 0..9; a qubit with `protectedUntil > now` rejects H/X/CNOT/MEASURE/MUTATE on it with 409 `{ error: "qubit protected", until }`; PROTECT sets protectedUntil = now + 30 min (max 3 protected at once, else 409); MUTATE applies RY with a random angle in [−π/2, π/2]; MEASURE returns the outcome. Rate limit per IP: bucket "pet", 1 action per 60 s (limit 1, period 60 s) → 429 `{ error, retryAt }`. On success: persist state, append pet_actions, increment actions_today, return `{ ok: true, outcome?: 0|1, state: PetState }`.
- `GET /api/pet/history?limit=30` → `PetDay[]` newest first (max 90).
- Cron (integrator wires `scheduled`): `export async function collapsePet(env): Promise<PetDay | null>` → if a collapse is due: measureAll, insert pet_days (p_top = probability of the measured string before collapse), start the next day (day+1, fresh state, protected '{}', actions_today 0), then `postDayToX(env, day)` from worker/x.ts (skip silently when X secrets are missing; record posted_at on success). Idempotent: a second call in the same UTC day is a no-op.

### Signed gates and badges (track D, SPEC 3.6)
Storage, `migrations/0006_pet_wallet.sql` (ALTER TABLE ADD COLUMN has no IF NOT EXISTS: wrangler runs the file once):
```sql
ALTER TABLE pet_actions ADD COLUMN wallet TEXT;                       -- NULL for an anonymous gate
CREATE INDEX IF NOT EXISTS pet_actions_wallet ON pet_actions(day, wallet);
CREATE TABLE IF NOT EXISTS pet_nonces (nonce TEXT PRIMARY KEY, wallet TEXT NOT NULL, at INTEGER NOT NULL);
CREATE INDEX IF NOT EXISTS pet_nonces_at ON pet_nonces(at);
CREATE TABLE IF NOT EXISTS pet_badges (wallet TEXT NOT NULL, day INTEGER NOT NULL, kind TEXT NOT NULL, PRIMARY KEY (wallet, day, kind));
ALTER TABLE pet_days ADD COLUMN top_wallet TEXT;
ALTER TABLE pet_days ADD COLUMN top_gates INTEGER;
```
Shared helpers in `src/lib/petGate.ts` (pure, package imports only; the Worker imports it as `../src/lib/petGate`):
- `GATE_MESSAGE(day, gate, q, t, nonce)` = `dirac:pet:gate:v1:<day>:<gate>:<q>:<t or ->:<nonce>`; `newGateNonce()` = 16 random bytes as 32 lowercase hex; `isGateNonce`, `isWalletAddress`, `verifyGateSig(wallet, message, sig)` (Ed25519 via @noble/curves, base64 or base58 signature, never throws); `SIGNED_PET_LIMIT = 3`, `ANON_PET_LIMIT = 1`, `PET_WINDOW_MS = 60_000`, `windowOf(now)`.
- Browser: `signGate(day, gate, q, t, wallet)` → `SignedGate { day, wallet, nonce, sig }` (one `wallet.signMessage`, throws what the wallet throws so the caller can fall back to anonymous); `fetchPetState(wallet?)`, `applyGate(gate, q, t?, signed?)`, `fetchPetBadges(wallet)`; errors are `PetGateError { status, retryAt }` (429 message names the wait).

Routes:
- `POST /api/pet/act` also accepts `{ day, wallet, nonce, sig }` next to `gate, q, t`. `wallet`, `nonce` and `sig` go together (else 400) and need `day` (400). Checks, in order:
  1. Pre-check, one read-only D1 batch before anything else: if the IP's `petbad` count, the IP's `pet` count (anonymous) or the wallet's `petw` / the IP's `petip` count (signed) has already reached its limit in the current window → 429 `{ error: "rate limited", retryAt }`; a signed nonce already in `pet_nonces` → 409 `{ error: "nonce already used" }`. Nothing is written and no state is read.
  2. `day` (when sent, signed or not) must equal the current register day, else 409 `{ error: "day mismatch, …", day }`; the signature must verify over `GATE_MESSAGE(currentDay, gate, q, t, nonce)` with the wallet key, else 401 `{ error: "bad signature" }`; the gate rules (protection) as before.
  3. Signed only, the Sybil caps (`migrations/0009_pet_sybil.sql`): the wallet is added to `pet_wallet_ips(utc_day, ip_hash, wallet)` while the IP (hashed like `pet_actions.client`) has fewer than `WALLETS_PER_IP_PER_DAY` = 3 wallets that UTC day, else 403 `{ error: "… already signed with 3 wallets today …", limit }`; then the wallet must have an account on Solana: `getAccountInfo` through the Worker's RPC rotation (`handlePet`'s sixth argument `{ rpc }`), cached in `pet_wallets(wallet, on_chain, checked_at)` for a day when found and five minutes when not, else 403 `{ error: "this wallet has no account on Solana yet …" }`. An RPC that cannot answer lets the gate through, uncached.
  4. The limit, incremented only now so a refused gate spends no slot: signed gates count in bucket `petw` keyed by wallet (`SIGNED_PET_LIMIT` = 3 per minute) and in bucket `petip` keyed by IP across wallets (`SIGNED_IP_LIMIT` = 6 per minute); anonymous ones in bucket `pet` keyed by IP, 1 per minute (429 either way).
  5. One D1 batch applies the state, logs the action and (signed) spends the nonce with `INSERT OR IGNORE INTO pet_nonces`; the state update and the action row are guarded by `NOT EXISTS (nonce)`, so a nonce raced by its own replay applies nothing and answers 409 `{ error: "nonce already used" }`. A rate-limited or refused request therefore never writes a nonce row.
  Every refusal after the pre-check (401, 403, 409) is counted in bucket `petbad` keyed by IP, 20 per minute, after the response. The action row stores `wallet`; the returned `state` carries `myGates` for the signing wallet. Nonces older than two days, `pet_wallet_ips` rows older than yesterday and wallet checks older than 30 days are pruned opportunistically (a nonce is bound to its day, so it can never verify again).
- `GET /api/pet?wallet=<base58>` → `PetState` plus `myGates` (the wallet's signed gates today). Without the query `myGates` is null. Every response now has `signedToday` and `leader: { wallet, gates } | null` (the wallet with the most signed gates so far today, ties to the one that reached the count first). A malformed wallet is 400.
- `GET /api/pet/history` rows carry `topWallet` and `topGates` (null for days before this migration or with no signed gate).
- `GET /api/pet/badges?wallet=<base58>` → `PetBadge[]` newest day first, influencer before witness within a day, max 90: `{ wallet, day, kind: "witness" | "influencer", form, measuredAt, gates }` where `form`/`measuredAt` come from the day row and `gates` is the wallet's signed gates that day. Missing or malformed wallet: 400.
- `collapsePet`: before the batch it ranks the day's signed wallets (`COUNT(*) DESC, MAX(at) ASC, wallet ASC`); the batch writes the day row with `top_wallet`/`top_gates`, `INSERT OR IGNORE` a `witness` badge for every wallet with a signed gate that day and an `influencer` badge for the top wallet. All idempotent, so the isolate that loses the day guard writes nothing new.
- Client: `GatesPanel` signs every gate with the connected wallet (`useWallet`), shows "signed by <wallet>", the per-minute allowance left and the badge forecast ("sign one gate for the witness badge" / "witness + influencer, leading with N" / "witness · influencer needs more than N"), and falls back to an anonymous gate when the wallet refuses; a 403 from the Sybil caps shows as the gate error with the server's message. Its copy names the anonymous limit as per network address (the bucket is keyed by IP, so visitors behind one router share it). `usePet({ wallet })` passes the wallet to the reads and tracks the wait per wallet. `/pet` mounts `PetBadgesPanel` (src/components/pet/PetBadges.tsx) with the connected wallet; `HistoryList` shows each day's influencer linked to `/p?a=`; `/p` shows one `Pet badges` row (`<PetBadges wallet />`) both in the details list of a passport and in the not-found panel, since any wallet can sign gates without a passport.

### Sundays on IBM quantum hardware (SPEC 3.6)
The Sunday 00:00 UTC collapse (`isQpuCollapse(collapseAt)`: the scheduled collapse instant is a Sunday, even when the collapse itself runs late) is measured on a real IBM quantum computer when everything below holds; otherwise the simulator draws it as on any day and the day row says why (`qpu_note`). Code: `worker/qpu.ts` (pure transpiler, result parser, quota rules, REST client; no D1), `worker/pet.ts` (tables and the state machine), `migrations/0012_pet_qpu.sql`, self-test `node scripts/qpu-selftest.ts`.

Eligibility, checked in `collapsePet` before the batch (`planHardware`): the `IBM_QUANTUM_API_KEY` secret is set; no run is open (`submitting | queued | running`); the QPU seconds recorded since the 1st of the UTC month, Sunday runs and smoke jobs (`qpu_smoke`, below) together (a job without reported usage counts 30 s), are under 480 (8 of the Open plan's 10 minutes); the day's log is complete (`pet_actions` rows by id = `actions_today`, every MUTATE has its `theta`, every MEASURE its `outcome`); replaying the log from the day-start state (MEASURE forced to the logged outcome) gives the stored state with fidelity ≥ 1 − 1e-6 (a gate lost to a concurrent write fails this); the compiled circuit has at most 600 CZ; the day's MEASURE outcomes are likely enough that at least 20 of the 1001 shots should repeat them (`replayWithOdds(log).pMids × 1001 ≥ MIN_EXPECTED_MATCHES`, see post-selection below).

Post-selection: the chip draws its own outcomes for the day's partial measurements, so a shot is a draw of the site's register only when its `m` register equals the site's logged outcomes. The collapse is the first such shot (the 1-shot collapse pub first, then the distribution pub in order: shots are independent, so it is a fair draw of the same conditional distribution); the published histogram and the comparison use only those shots (`compare.shots`, out of `compare.totalShots`). A completed job with no such shot falls back with the reason. Without partial measurements every shot counts.

Collapse of an eligible day: one batch starts the next day (same guard), inserts `pet_qpu_runs` (status `submitting`, the stored state JSON, the site's mid-circuit outcomes, the CZ count) and awards the witness/influencer badges. Two collapses can run at once (both crons fire at 00:00, a visit collapses lazily) and a losing one may have planned the simulator (it sees the winner's run as pending): `SQL_INSERT_DAY` writes nothing for a day that has a `pet_qpu_runs` row, and `SQL_QPU_START` nothing for a day that has a `pet_days` row. No `pet_days` row yet: `SQL_BODY` keeps the previous body, and `/pet` shows a "measuring on ibm_xxx" chip next to it. `collapsePet` returns null and runs `pollQpu` (after the response when lazy).

`export async function pollQpu(env): Promise<void>` (never throws): picks the oldest open run and claims it (`polled_at` moves only if the last poll is ≥ 60 s old, so isolates do not poll twice; a `submitting` run is claimed for 5 minutes, `SUBMIT_LEASE_MS`, since a submission makes up to a dozen IBM calls of up to 20 s each, and `SQL_QPU_SUBMITTED` ends the lease), then:
- `submitting`: IAM token (isolate cache), instance CRN (`IBM_QUANTUM_CRN` or the Resource Controller listing, Open plan first), IBM's own allowance (`GET /v1/instances/usage`, < 60 s left → fallback), backends by queue length (online, ≥ 10 qubits), the first CZ target (basis has cz, rz, sx, x; measure supported) with a line of 10 healthy coupled qubits (calibration from `/properties` when available: broken couplers and noisy qubits avoided, lowest summed readout + CZ error), then `POST /v1/jobs` → `queued` with crn, backend, job id, chain and the QASM. A failure counts an attempt (reason kept) and pushes the next claim 20 minutes out; the third failure falls back. A retry (an attempt was counted, or a poll claimed the run before and was cut off without recording anything, `polled_at` not null) first looks up a job already tagged `dirac-pet-day-<N>` and adopts it; a lookup that fails counts as a failed attempt rather than sending blind. Failure texts are published (`reason`, `qpu_note`), so `publicReason` masks instance CRNs and caps them at 300 characters.
- `queued | running`: `GET /v1/jobs/{id}`; Completed → results + metrics → settle on hardware (fallback when no shot repeated the site's partial measurements); Failed / Cancelled → fallback with IBM's reason; still open six hours after the collapse → cancel (best effort) and fallback; otherwise the status is recorded.
- Settle (one batch, guarded by the status read): the run gets `done | fallback`, bits, the collapse shot's mid-circuit outcomes, the histogram of the shots that repeated the site's partial measurements, matched shots, the comparison summary, usage seconds, `finished_at`, and drops the state; `pet_days` gets the day with `source` (`qpu` / `simulator`), `qpu_backend`, `qpu_job`, `qpu_note`, `measured_at` = IBM's finish time (hardware) or the settle time (fallback), `p_top` = the simulator probability of the drawn string (it can be 0 on hardware: noise). Then the X post.

Circuit (`buildCircuit`): |0…0⟩, H on all ten, the logged gates in id order (PROTECT is not a gate; H·H, X·X and CNOT·CNOT cancel and RY angles merge when nothing touches their qubits in between), MEASURE as a mid-circuit measurement into `m[k]`, then `c[q] = measure` for every logical qubit. Logical qubit q starts on position q of a line of 10 physical qubits; a CNOT between non-neighbours moves the control along the line with SWAPs (the layout is tracked, no swap back; heavy-hex has no 10-cycle). Native set: H = RZ(π/2) SX RZ(π/2), RY(θ) = SX RZ(θ+π) SX RZ(π), CNOT = H(t) CZ H(t), SWAP = 3 CNOT, adjacent H·H cancelled, RZ runs merged. Emitted as OpenQASM 3 on physical qubits (`$n`), `include "stdgates.inc"`. Job: `{ program_id: "sampler", backend, tags: ["dirac-pet-day-N"], params: { pubs: [[qasm, null, 1], [qasm, null, 1000]], version: 2, support_qiskit: false } }` with `Authorization: Bearer`, `Service-CRN`, `IBM-API-Version: 2026-04-15` (the live version per the public `GET /api/v1/versions`). Results: `results[i].data.c.samples` (hex, bit k = logical qubit k) and `results[i].data.m.samples` (read as BigInt, so more than 53 partial measurements compare exactly); `results[0]` is the collapse pub, `results[1]` the distribution, post-selected as above. IBM job pages are private to the account, so the page publishes the id only.

Routes: `GET /api/pet` adds `qpu: PetQpu` and lazily runs `pollQpu` (after the response) when a run is open and was not polled in the last minute. `GET /api/pet/qpu` → `PetQpuRun[]` (newest 12); `?day=N` → that run plus `qasm`; `&format=qasm` → the circuit as `text/plain` (404 when none). History and body rows carry `source`, `qpuBackend`, `qpuJob`, `qpuNote`; `PetAction.theta` is the MUTATE angle.

Integrator: cron `"*/15 * * * *"` next to `"0 0 * * *"`, and `scheduled` runs `collapsePet(env)` then `pollQpu(env)` on every tick; `Env` gains `IBM_QUANTUM_API_KEY?` and `IBM_QUANTUM_CRN?`; apply migration 0012 before deploying (the queries read the new columns).


Page: `QpuPanel` (src/components/pet/QpuPanel.tsx, `#hardware` on /pet) shows the open run (backend, status, job id, sent time, circuit, the fallback time) or the next hardware collapse (or that runs are not switched on), the latest settled run (collapse bits, job id, finish time, CZ count and physical qubits with a link to the QASM, QPU time, partial measurements, hardware vs simulator by form with the Hellinger fidelity, or the fallback reason) and this month's QPU time. `HistoryList` marks every day with a chip (`ibm_xxx` or `simulator`), the job id, the note of a Sunday that stayed on the simulator, and heads the list with the day being measured.

#### Verifying the live IBM path before a Sunday
Two public routes let the owner prove the IBM side from production before the first hardware Sunday, without a key ever leaving the Worker. Code: `runQpuCheck`, `submitSmoke`, `readSmokeResult`, `smokeVerdict`, `scrubSecrets`/`publicReason` in `worker/qpu.ts`; the handlers, `pollSmoke` and the SQL in `worker/pet.ts`; `migrations/0014_qpu_smoke.sql` (apply before deploying: `SQL_QPU_MONTH`, read by `GET /api/pet` and the Sunday guard, now sums `qpu_smoke` too).

- `GET /api/pet/qpu/check` → `{ configured, ready, steps: [{ step: "iam"|"instance"|"usage"|"backends"|"chain", ok, detail, ms }], chosen: { backend, chain, calibrated } | null, candidates: [{ name, status, queue, qubits, usable, rank, evaluated, chain, detail }], checkedAt, cached, budget: { monthSeconds, monthBudgetSeconds } }`. Read-only: it runs the Sunday's own steps and submits nothing: a fresh IAM exchange (`exchangeApiKey`, not the isolate cache), the instance (`IBM_QUANTUM_CRN`, or the Resource Controller listing with the Open plan first; the detail names the plan, the region and the API host, never the CRN), `GET /v1/instances/usage` in words (used, limit, left, period end; an unreadable answer is `ok: false` but does not clear `ready`, as a Sunday goes ahead without it; a used-up allowance clears it), `GET /v1/backends` (every device with `status.name`, `queue_length`, `qubits`; the keys-only payload shape when nothing could be read) and `chooseTarget`, the Sunday's own choice (least busy first, at most 4, first CZ target with a line of 10 healthy coupled qubits, calibration when `/properties` answers). Every step is listed once, in order; after a failed step the later ones say `not run: the <step> step failed`. `ready` = iam, instance, backends and chain passed and IBM does not report the allowance used up. `ms` is wall time (in Workers the clock only moves across I/O, so the CPU-bound chain search reads near 0). Every detail passes through `publicReason` with the key, the token and the CRN as literal secrets on top of the patterns. Unconfigured: `{ configured: false, ready: false, steps: [], … }`. Limits: 2 requests a minute per client IP (bucket `qpucheck`, 429 `{ error, retryAt }`); a live result is stored in `qpu_check` and served to every caller for 5 minutes (`cached: true`); one isolate at a time runs a live check (claim in `qpu_check.claimed_at`, 2 minutes), the others answer the previous result (or 409 when there is none yet). IBM is therefore asked at most once per 5 minutes.
- `POST /api/pet/qpu/smoke` sends one small real job: a Bell pair (H on the first qubit, CNOT to the second, both measured into `c[0]`, `c[1]`) through the Sunday's backend choice, `toNative` and the QASM emitter (`emitIsaQasm`, which `emitQasm` wraps for the line of 10), on the neighbouring pair of the chosen line with the lowest summed readout and CZ error (`pickPair`; a coupler in the coupling map that passed the same health filter), as the Sunday's Sampler V2 body (`program_id: "sampler"`, a 1-shot pub then a 200-shot pub, `version: 2`, `support_qiskit: false`) tagged `dirac-qpu-smoke-<id>-<created_at>`. Refusals (409 `{ error, retryAt, smoke, budget }`): a smoke job pending; a Sunday run open; a smoke job that ran (completed, or was charged QPU time) less than 6 days ago (`retryAt` = then + 6 days); an attempt of any outcome less than 10 minutes ago (a submission that never reached IBM, or an IBM-failed job with no charged time, blocks only this long); the monthly budget used up (the same `SQL_QPU_MONTH` the Sunday guard reads, smoke rows included); IBM reporting under 60 s left on the instance. The attempt row is inserted under the same rules in one statement (`SQL_SMOKE_INSERT`), so racing requests send one job at most. 202 `{ ok: true, smoke }` when IBM took the job, 502 `{ error, smoke }` when it did not (scrubbed reason; a submission whose answer was lost is looked up by its tag before failing). 503 without the key. 2 requests a minute per client IP (bucket `qpusmoke`).
- `GET /api/pet/qpu/smoke` → `{ smoke: QpuSmoke | null, polled, next: { allowed, reason, retryAt }, budget }`. ### Routes (worker/inbox.ts)
- `POST /api/inbox/:to` body `{ envelope, sender, sender_sig }`: `to` and `sender` must be valid wallets; recipient must have a passport row (else 404 `{ error: "recipient has no passport" }`); envelope shape and base64 lengths checked (kem_ct 1088 bytes, nonce 24, ct ≤ 16 KB); verify `sender_sig` as Ed25519 over utf8(SEND_MESSAGE(to, envelopeHash(envelope))) with the sender's pubkey (import `envelopeHash`/`SEND_MESSAGE` from `../src/lib/inbox` and `ed25519` from @noble/curves); rate limit bucket "inbox-send" 10 per 60 s per IP and 30 per 60 s per sender; store; return `{ ok: true, id }`.

### USDC with a sealed note (SPEC 3.4 extension: invoices, salaries, OTC)
A letter can carry a USDC payment; the letter text is then the payment's private note. The amount and both wallets are public on chain, only the note is private.

Transaction (`src/lib/solana/usdc.ts` pure, `src/lib/solana/pay.ts` browser; hand-built with @solana/web3.js v1, no @solana/spl-token). One legacy transaction, fee payer = sender, three instructions in this order:
1. Associated Token Account program `ATokenGPvbdGVxr1b2hvZbsiqW5xWH25efTNsLJA8knL`, CreateIdempotent: data `[1]`; accounts payer (signer, writable), recipient ATA (writable), recipient wallet, mint, System program, Token program. Creates the recipient's USDC account when missing (the sender pays its rent, 0.00203928 SOL); a no-op otherwise.
2. SPL Token `TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA`, TransferChecked: data `[12, amount u64 LE, 6]`; accounts sender ATA (writable), mint, recipient ATA (writable), sender (signer). Mint `EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v` (USDC, 6 decimals).
3. SPL Memo `dirac:pay:v1:<first 32 hex of envelopeHash(envelope)>` (45 bytes, no signer accounts).

ATA = `PublicKey.findProgramAddressSync([owner, TOKEN_PROGRAM_ID, mint], ASSOCIATED_TOKEN_PROGRAM_ID)`. Exports: `USDC_MINT`, `USDC_DECIMALS`, `payMemo(hash)`, `parseUsdcAmount(text, maxDecimals = 2)` (the form takes cents), `formatUsdc(units)` (at least 2 decimals, up to 6), `associatedTokenAddress(owner, mint?)`, `createAtaIdempotentIx`, `transferCheckedIx`, `memoIx`, `usdcPaymentInstructions({ from, to, amount, envelopeHash })`, `decodeTokenAccount(data)`, `checkUsdcPayment(tx, { sender, recipient, amount, envelopeHash })`. Browser: `readPaymentAccounts(sender, recipient)` (one getMultipleAccounts through the /api/rpc proxy: sender SOL, sender USDC ATA balance and frozen flag, whether the recipient ATA exists, SOL needed = base fee + the recipient ATA rent when it is missing + `WALLET_RENT_RESERVE_LAMPORTS` 890 880, the rent-exempt minimum a fee payer must keep), `buildUsdcPaymentTx(req)`, `awaitPayment(signature)` → `"confirmed" | "failed" | "unknown"` (never throws).

Flow on `/write` (compose panel, "Attach USDC"): encrypt the letter, compute the envelope hash, sign `SEND_MESSAGE` (unchanged), build and send the payment through the wallet, wait up to 60 s, then `POST /api/inbox/:to` with `payment: { signature, amount }` (amount in base units). A transfer that failed on chain stops the send; one not confirmed in 60 s is posted anyway (the server keeps it pending). If the POST fails after the transfer, the sealed letter stays in the tab ("Transfer sent, letter not delivered", shown only after that failure) and "Deliver the letter" re-posts the same envelope: no second transfer. The amount field reads a comma as the decimal point (never drops it) and takes two decimals at most. Before sending, the page reads balances and keeps the button disabled until they are read, and with a message when the USDC balance is below the amount, the wallet has no USDC account, the account is frozen, SOL does not cover the fee, the rent when the recipient has no USDC account and the wallet's own rent minimum, or the balance cannot be read; paying yourself is refused.

Worker (`worker/inbox.ts`, `Env.RPC_URL?` first, then publicnode and api.mainnet.solana.com from worker/index.ts's list; the anonymous free endpoint solana.leorpc.com is left out because a forged answer would verify a payment):
- `POST /api/inbox/:to` accepts the optional `payment: { signature, amount }` (`parsePaymentClaim` in src/lib/inbox.ts: base58 64-byte signature, positive safe-integer base units or a string of digits, no other fields; else 400). `to === sender` with a payment is 400. After the existing checks (signature, rate limits, recipient passport): the same letter (to, sender, envelope, amount) already stored with that signature answers its id and payment again (idempotent retry); a signature already spent on another letter (`inbox_payments`) is 409 `{ error: "this payment is already attached to another letter" }`. Otherwise `getTransaction(signature, { encoding: "jsonParsed", commitment: "confirmed", maxSupportedTransactionVersion: 0 })`, polled for up to 10 s, and `checkUsdcPayment`: no error; a top-level USDC TransferChecked of exactly `amount` with 6 decimals, authority = sender, source token account owned by the sender (pre/post token balances), destination = the recipient's ATA; a top-level memo equal to `payMemo(envelopeHash)`. Inner (CPI) transfers are not counted. A transaction version above 0 is invalid. Answer `{ ok: true, id, payment: { signature, amount, status, reason } }`, status `verified` (the signature is claimed in `inbox_payments`), `invalid` (stored, with the reason) or `pending` (not visible yet, or no upstream answered).
- `GET /api/inbox/:wallet`: every message carries `payment: LetterPayment | null`. Before answering, up to 5 pending payments not looked at in the last 20 s are re-checked in parallel within 6 s, at most 12 reads with re-checks per wallet per minute (bucket `inbox-paycheck`). Each "not visible" answer spends one of 8 checks; the 8th makes the payment invalid ("the transaction was not found on chain after 8 checks"). An unreachable RPC spends nothing.
- Uniqueness: the verified transition is one D1 batch: `INSERT OR IGNORE INTO inbox_payments`, settle this letter to verified (or invalid "already attached to another letter" when another letter holds the claim), and mark every other letter still pending on that signature invalid. A deleted letter's `inbox_payments` row stays, so the signature remains spent.
